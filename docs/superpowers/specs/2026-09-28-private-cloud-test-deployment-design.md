## 4. 部署结构与持久化

### 4.1 单机运行结构

请求链路为：家庭浏览器 → HTTPS 与全站认证入口 Caddy → 仅监听 `127.0.0.1:3001` 的 Fastify → 本机 SQLite 和媒体文件。

- 保留 Node.js 24 主版本，实施时固定一个当时受支持的 24.x 补丁版本并记录，不自动升级主版本。
- 生产环境使用构建后的前端和服务端，不运行 Vite 开发服务器或文件监听模式。
- Fastify 继续同时提供网页、曲库和媒体接口；不将媒体目录交给 Caddy 直接提供静态下载。
- 用 systemd 管理单个应用进程，以专用非 root 用户运行，支持开机启动、异常重启和正常退出。SQLite 不放在网络文件系统或对象存储挂载目录。
- 采用单进程、单数据库写入边界，不使用多副本自动扩容。维护期间允许个人测试环境短暂停机。

### 4.2 服务器目录约定

以下是后续服务器配置的设计路径，本规格写入不会在本机或云端创建这些目录。

| 路径 | 用途与生命周期 |
|---|---|
| `/srv/255-phonograph/releases/` | 每次发布的独立代码和构建产物；部署仅切换已验证版本。 |
| `/var/lib/255-phonograph/` | `PHONOGRAPH_DATA_DIR` 的绝对真实路径，保存 `library.sqlite`、WAL 相关文件及 `media/`。禁止把该路径或祖先替换为符号链接，以适配现有本地存储检查。 |
| `/var/backups/255-phonograph/` | 备份暂存及未完成上传的加密包，不作为网页目录；限制容量和访问权限。 |
| `/etc/255-phonograph/` | 生产配置及受限凭据文件，位于仓库与网页目录之外。 |
| Caddy 的独立持久化目录 | 证书、私钥与续期状态；更新应用时保留。 |

代码发布目录可以使用版本选择机制，数据目录不得随发布版本变化。部署前校验真实数据路径、权限及磁盘空间；已有部署数据目录意外缺失时应失败退出，不能自动用空数据库“恢复服务”。首次初始化由明确的部署步骤完成，不能由路径拼写错误触发。

重启进程、重启服务器及重新部署不得删除数据库或媒体。重装系统、销毁实例、磁盘损坏和欠费释放并不在“持久化目录”保障范围内，需靠独立备份恢复。系统盘上的另一份文件不是独立备份。

应用日志不得包含明文密码、Cookie、Authorization、存储密钥、备份解密密钥、请求正文或完整上传内容。限制日志留存和总容量；磁盘使用率达 80% 提示，达 90% 拒绝新的媒体上传并保留现有播放与管理能力，备份还需单独核算暂存空间。不得通过自动清除正式媒体腾空间。

## 5. 访问与管理员保护

### 5.1 全站私人入口

- Caddy 在 HTTPS 层使用独立用户名和强密码的 Basic Authentication，覆盖网页、静态资源、所有 `/api` 请求及 GET/HEAD/Range 媒体请求。该凭据与应用管理员密码分开。
- 所有者首次打开网页时由浏览器提示输入私人访问凭据，无需安装客户端。Basic Authentication 的浏览器凭据缓存与应用退出登录不同；退出后台只撤销管理员会话。撤销全站访问需更换入口凭据，验收应使用新浏览器会话验证。
- Caddy 配置保存密码哈希，不保存明文。凭据及哈希均不写入仓库。HTTP 只负责跳转 HTTPS 或证书验证，不在明文 HTTP 上收集凭据。[认证行为依据](https://caddyserver.com/docs/caddyfile/directives/basic_auth)
- 未经全站认证的新请求返回 401，不泄露曲库、媒体内容或管理设置；HTTPS 证书验证所需协议路径可以按 Caddy 的标准机制处理，但不开放应用内容。
- 只开放必要的 Web 端口；SSH 使用密钥和受限运维来源。应用端口、数据库、备份目录不开放公网。IP 直连、错误 Host、备用域名不能绕过入口认证。
- 入口认证成功后，在转发应用请求时移除全站 Authorization 凭据；转发来源信息只信任本机入口，不信任外部伪造的转发头。

### 5.2 应用管理员会话

保留当前密码哈希、HttpOnly、SameSite=Strict 和服务端会话验证；云端明确启用 `Secure` Cookie。当前 `secureCookies` 只有构造参数、生产启动未启用的问题必须在实施阶段补齐，并保留本地 HTTP 开发使用方式。

管理写接口除现有会话验证外，检查生产站点 Origin；跨站和缺少所需来源的写请求被拒绝，允许的非浏览器运维操作需要走明确认证方式，不能全局关闭检查。首次密码设置只能在受保护入口内由所有者完成；沿用现有已配置密码的状态约束，不提供或执行密码重置。

对首次设置、登录和改密码配置速率限制，失败有明确 429/重试反馈，不采用永久账号锁定。全站入口也需有限的失败尝试抑制，不只保护应用登录页；可由标准入口日志与主机防护组合实现，具体文件与参数在实施计划中列出并验证。限制不能影响正常的音频 Range 请求。

云端测试默认初始化独立数据目录。若使用全新数据库，由所有者创建云端管理密码；这不修改本地管理密码。若以后批准迁移本地数据库，保留迁移后的密码哈希，但撤销复制过来的旧管理会话，要求在云端重新登录。

## 6. 媒体访问、Range、跨域与缓存

### 6.1 媒体权限

当前普通曲库接口筛选已发布歌曲，但 `server/routes/media.ts` 只按媒体编号查找 `media_objects`，未检查关联歌曲状态。上线前必须补齐状态边界：

- 外部请求先通过全站入口认证。
- 现有普通媒体接口只返回仍被已发布歌曲引用的音频和封面；未被已发布歌曲引用的草稿、下架、回收站及孤立媒体返回 404。
- 同一个媒体被其他已发布歌曲引用时，仍可按那份有效引用访问；不得只检查某一条失效关联。
- 管理员登录本身不自动绕过普通媒体接口的发布状态检查。本阶段不新增未发布媒体预览；如未来需要预览，应另设验证管理员权限的明确接口。
- 下架、替换、删除后，旧地址的新请求按最新状态处理。已传送到浏览器或已经开始的响应无法撤回，不强行打断现有流，也不承诺清除浏览器已有数据。
- 不暴露真实磁盘路径、内部存储键、备份桶地址或凭据；随机编号不是访问控制的替代品。

### 6.2 音频请求

保留单段字节 Range，测试普通 GET、HEAD、前缀/开放结尾/后缀范围、有效 206、无效 416 和资源不存在。核对 `Accept-Ranges`、`Content-Range`、`Content-Length` 与 MIME；HEAD 不返回正文。

入口不得整文件缓冲后才发送、压缩变换音频字节、丢弃 Range 或把 206 合并为 200。浏览器中验证首次播放、反复拖动、从末尾拖回开头、恢复已保存进度、自动下一首及长时间播放。不能用接口测试替代真实播放器体验。

### 6.3 同源与缓存

- 页面、API、音频、封面、歌词保持同一 HTTPS 来源，不新增宽泛跨域允许配置。备份桶不启用浏览器 CORS，也不提供公共下载链接。
- 曲库、歌词、媒体、管理员接口与认证错误响应使用 `Cache-Control: private, no-store`，首轮测试不加 CDN 或共享代理缓存。这样新请求会重新经过权限与状态判断，但仍不等于能撤回已经加载的媒体。
- 带内容哈希的前端静态文件可以在全站认证之后使用私人浏览器缓存；首页 HTML 要求重新验证或不缓存，避免部署后长期使用旧入口。
- 更换域名或跨源部署属于后续方案变更；届时需重新验证音频跨域属性、频谱分析、凭据、Range 和缓存，不能直接开启 `Access-Control-Allow-Origin: *`。

## 7. 上传与对象存储边界

### 7.1 已确认的耦合

`UploadService` 持有 `mediaDirectory`，在建立临时上传后执行 `path.join(this.mediaDirectory, 'tmp', temporaryKey)`，把磁盘路径交给文件类型检测与时长探测。`MediaStore` 虽抽象了临时写入、正式化、打开及删除，却没有定义供校验器读取临时内容的能力。

因此，只把 `LocalMediaStore` 换成云适配器会使校验过程仍访问错误的本地路径。现有本地正式化依赖同文件系统 rename，也不能当作对象存储跨服务的原子事务。

### 7.2 本阶段决定

保留现有本地上传和正式媒体存储，不重构该边界。音频 200 MB、封面 10 MB、LRC 1 MB 及类型、时长校验继续有效；入口上传限制要为 multipart 开销预留空间，不能把应用合法上限提前截断。数据库和媒体路径都在独立数据目录内。

备份上传是独立的运维能力，输入为已完成、已加密的备份包，不调用业务上传接口、不进入 `pending_uploads`、不建立歌曲、不返回播放地址。

### 7.3 未来正式媒体云存储的约束

后续若单独批准对象存储重构，应分开定义：

- 本地校验暂存区：负责容量限制、进度、取消、清理，以及受控临时读取句柄。业务服务不拼接存储内部目录；需要文件路径的检测器由暂存区在受控生命周期内提供路径。
- 正式媒体仓库：接收已经验证的内容，写入随机且不可变的对象键，并返回内部引用；支持有范围的读取、HEAD/元数据和幂等删除。
- 业务提交协调：对象上传和数据库提交无法共享本地事务，需明确上传完成、数据库引用建立、失败补偿、孤立对象清理及重试规则，不能照搬 rename 的原子性。
- 媒体分发：默认私有桶、服务端按歌曲状态授权并代理 Range。若以后采用短期签名直链，必须单独设计链接有效期、下架后撤销窗口、跨域与缓存行为；不把 Referer、防盗链或难猜 URL 当作用户权限。
- 未完成 multipart 上传、取消上传和校验失败都需有有界清理策略，避免隐藏存储费用。

这些是边界设计，不授权当前实施正式媒体云存储、前端直传或修改现有播放器数据结构。

## 8. 加密备份与恢复

### 8.1 一致备份流程

默认每日北京时间 05:00 尝试一次，目标是上一次成功备份距今不超过 24 小时。该时间和周期作为后续运维配置；启用前须批准服务器产物目录、桶前缀、执行频率及保留范围，不在本会话创建任何定时任务。

1. 检查单任务锁、上次备份状态和暂存空间，进入受认证保护的维护状态，阻止新上传及管理写入。
2. 等待在途请求结束并正常停止应用，确认进程退出和无其他数据库写入者。退出超时或数据库状态不明确时，标记本次备份失败，不能把不确定的复制包标为成功。
3. 在同一停写窗口制作数据库一致快照并复制对应媒体，包含暂存媒体与对应待处理记录；不靠运行时只复制一个 `library.sqlite` 文件。可用 SQLite 备份 API 制作自洽的数据库副本；不会把在线数据库快照误当作媒体也同时冻结。[SQLite 备份机制](https://www.sqlite.org/backup.html)
4. 记录数据库 schema 版本、应用提交、备份时间、文件清单、大小与 SHA-256；在暂存副本上运行数据库完整性检查，并检查正式媒体引用是否都有文件。可选的旧孤立文件不作为活动歌曲恢复。
5. 本地副本完成后及时恢复应用并检查健康状态，再对稳定副本加密、上传到私有备份桶；远端上传失败不延长应用停机。异常路径也必须尝试安全恢复服务，并报告是否恢复成功。
6. 使用随机备份编号作为对象键；文件清单置于加密包内。上传完成后验证远端对象存在及长度，并保存独立密文校验值；不把 multipart ETag 直接当作完整文件 SHA-256。
7. 仅在新备份确认成功后，清理超过最近 7 份的旧成功备份。失败备份不能挤掉最后可用备份；不在所有者未批准的桶前缀删除任何对象。

维护窗口目标为 10 分钟以内，实际耗时需通过试运行记录。恢复点目标为 24 小时以内，失败或未开机期间不保证达成；显示最后一次成功时间，不只显示定时任务存在。

### 8.2 凭据与保留策略

备份包使用成熟的公钥加密工具：服务器仅保留加密所需的公钥，解密私钥由所有者在服务器之外保管，并确认有可恢复副本。工具选择、文件名和验证步骤在实施计划中列出。私钥、密码和云密钥不进入 Git、聊天输出或公开日志。

备份桶禁止公共读写、列表访问及静态网站托管。使用仅作用于指定桶/前缀的最小权限凭据；备份写入/轮换与人工恢复读取权限分别控制。服务器和备份桶的生命周期分开，不随删除实例自动清空备份。首次恢复演练必须证明真实下载、解密、校验和重新启动都可完成，不能只凭远端对象存在判断可恢复。

数据库与媒体来自同一备份集。管理员密码哈希属于加密备份内容；复制的管理会话在恢复副本中撤销，不重置密码。访问入口凭据、云密钥和解密私钥不随曲库备份分发，恢复时由所有者重新提供受限配置。

### 8.3 恢复演练
